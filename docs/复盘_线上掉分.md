# 复盘：为什么本地涨了、线上反而掉了 4 分

## 事实

| 提交 | 本地(dev, A档) | 线上综合 | 线上 A | 线上 B | 线上 C |
|---|---|---|---|---|---|
| v1 | 77.14 | **72.06** | 73.74 | 73.07 | 58.92 |
| v2 | 78.61 | **68.08** | 69.27 | 69.62 | 56.33 |
| v3 | 80.57 | 待测 | — | — | — |

本地涨 1.47，线上掉 3.98。**代理评分器判断反了。**

## 定位过程

### 1. 先做文件级 diff（排除"是不是哪里错了"）

```
证据链完全相同：760 / 760 = 1.000      ← 链解码没变，问题不在链
答案完全相同  ：447 / 760 = 0.588
置信度完全相同：  95 / 760 = 0.125（拒答）
置信度均值    ：v1=0.696  v2=0.598
```

链一字未改 ⇒ 掉分只能来自答案与置信度。

### 2. 客观缺陷指标（不依赖评分器）

| 版本 | 含外来事件 ID | 方向颠倒 | 答案 ID 顺序与提交链一致 |
|---|---|---|---|
| v1 | 2.4% | 2.0% | 58.8% |
| v2 | 1.4% | 1.4% | **50.1%** |
| v3 | **0.0%** | **0.0%** | **76.2%** |

### 3. 根因一：我把组合结构选错了

v2 的"答案槽位对齐"用了**线性指派问题**（Kuhn-Munkres）。指派问题是为**集合**设计的，
允许任意置换；而证据链是**有序序列**，顺序本身承载因果方向。
实测（同一次检索结果，只换对齐方式）：

| 对齐方式 | 代理答案分 | 与提交链一致 | 与金标同向 |
|---|---|---|---|
| 按位置（v1） | 23.42 | **1.000** | **0.846** |
| 单调 DP | 23.01 | 0.857 | 0.757 |
| 指派（v2） | **23.83** | 0.750 | 0.649 |

**指派法的代理分最高、顺序保真度最差。** 代理评分器只算内容覆盖、对顺序与方向不敏感，
于是它奖励了"把内容堆进去、顺序随便打乱"的答案——正好与官方评分器相反。

> 教训：有序结构要用**单调序列对齐**（Needleman-Wunsch / DP），集合结构才用指派问题。

### 4. 根因二：两个从第一版就存在的答案缺陷

1. **括号里的类型名一直是模板的，不是本 pack 的真实类型。**
   例如本 pack 的 D002 是"深度报道"，答案却写 `D002（司法追责）`——ID 与类型自相矛盾，
   在评判看来就是事实错误。
2. **模板槽位多于链节点时，多余的槽位没有被处理**，外来事件 ID 会残留在答案里
   （v1 占 2.4%，C 档更严重）。

### 5. 根因三：置信度尺度建立在错误的度量上

v2 的校准目标是**我们自己代理评分器算出的正确率**（均值 0.603），而代理评分器本身
系统性低估（它的金标上界只有 0.775）。于是置信度整体被压低到 0.598，
而 v1 在 0.696 时线上表现更好——说明官方尺度的真实正确率更接近 0.7 而非 0.6。

## 修复（v3）

| 修复 | 做法 |
|---|---|
| 回到保序映射 | `align_mode=positional`（与提交链一致率 1.000），指派/DP 保留为可选 |
| 类型名改写 | 把 `ID（xxx）` 里的 xxx 一律换成该 ID 在本 pack 的真实类型 |
| 多余槽位删除 | 模板槽位多于链节点时整段删掉，不再重复指向同一节点 |
| 外来 ID 安全网 | 任何不属于本 pack 的事件 ID 一律剔除（构造性保证，不靠运气） |
| 置信度等价化 | `conf = 0.7 + 0.25·(c_hat/0.775 − 0.7)`：先用"代理评分器上界"把尺度折算到官方尺度，再向已知可用的工作点 0.7 收缩 |

## 新的验收门槛（这次学到的）

在这一类"评分器只是代理"的场景下，**任何答案层改动必须同时通过客观缺陷检查**，
不能只看代理分：

1. 代理答案分不显著下降；
2. 答案 ID 顺序与提交证据链的一致率不下降；
3. 外来事件 ID 不增加；
4. 与金标的同向率不下降。

v2 的指派方案在第 1 条上通过、在第 2/4 条上失败——如果当时有这套门槛，就不会提交。
